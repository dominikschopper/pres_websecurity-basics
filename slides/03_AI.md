## AI-generated code: how secure is it?

- Veracode 2025: **45 %** of tasks produced vulnerable code (80 tasks, 100+ models)
- Failed to prevent XSS in **86 %** of samples, log injection in **88 %**
- Java worst: > 70 % failure
- 2026 report: pass rate **stalled at ~56 %**
- Functional ≠ secure

Note:
- source: Veracode GenAI Code Security Report 2025 + 2026
- vendor study (sells SAST) → direction, not exact numbers
- CWE-80 (XSS), CWE-117 (log injection) → Input 2 vocabulary
- "tests pass" says nothing about security

## Why does it happen?

- Trained on public code – **including the insecure parts**
- Optimizes for "works", not for **your** threat model
- No knowledge of your business rules, trust boundaries, data classes
- Looks plausible → **review fatigue**

Typical: missing authorization checks · unsafe input handling · hard-coded secrets · weak crypto · outdated APIs

- more code, faster → more to review
- ask the assistant for secure code explicitly – helps, no guarantee

## Hallucinated packages → "slopsquatting"

- Models suggest packages that **don't exist**
- Study (USENIX Security 2025): **19.7 %** of recommended packages were fake – 205,000+ unique names
- **43 %** of hallucinated names reappeared in *every* re-run → predictable
- Attacker registers the name → you `npm install` malware

**Defense:** verify before install · check age, maintainers, downloads · lockfile · review dependency diffs

Note:
- sources: Spracklen et al. 2025; Socket coined / popularised term
- 16 models, 576k code samples
- cousin of typosquatting, dependency confusion
- A03 from Input 1
- agent installs by itself → who checks?

## Your AI tools are attack surface

- Agents read files, run commands, hold **tokens and repo access**
- **Indirect prompt injection:** instructions hidden in README, issue, web page, dependency
- Plugins / MCP servers / extensions = **supply chain**
- Real precedent: stolen tokens powered the Shai-Hulud npm worm

**Defense:** least privilege · no prod secrets · sandbox · human approval for risky actions

Note:
- coding agent = a user with your permissions
- untrusted content in context = can steer the agent
- what can your agent do without asking?
- company policy: which tools, which data

## Attackers get faster

- Models now **find vulnerabilities and write exploits** autonomously
- Anthropic (Apr 2026): non-public model found thousands of high/critical vulns
- Microsoft Digital Defense Report 2026: discovery-to-weaponization median **well under 24 h**
- Google M-Trends 2026: time-to-exploit estimated **negative** – exploit before patch
- Widely available models already reach working exploits

**So:** patch faster · shrink attack surface · KEV first

Note:
- sources: CERT-EU blog, Microsoft DDR 2026, Forescout, Wiz
- numbers differ per source (hours to days) – direction matters
- vendor-reported, treat with care
- old rhythm "patch next sprint" no longer fits
- link: CVSS / KEV from Input 2

## Defenders get help, too

- AI-assisted code review, SAST triage, fuzzing, patch suggestions
- DARPA AIxCC: AI systems found *and fixed* flaws in real open-source code
- Use as **reviewer**, not as **authority**
- False positives and false negatives – **verify**

**Keep:** SAST · SCA · secret scanning · tests in CI – AI on top, not instead

Note:
- AIxCC: one system found 77 % of planted vulns (Intl. AI Safety Report 2026)
- give context: threat model, trust boundaries
- ask: "how could this be abused?"
- decision stays human

## Old rules, new context

- LLM output = **untrusted input** (before SQL, HTML, shell)
- Nothing secret in the system prompt – it will leak
- **Least privilege** for every tool the model can call
- Human approval for irreversible actions
- Log, rate-limit, cap cost

Note:
- A05 + A01 + A09 again
- allow-list tools, not "everything"
- treat retrieved docs as data, not instructions
- exercise idea: what could go wrong in our chatbot?
